# Active Nmap Basic Real Output Redaction Hardening Design

Decision:

```text

```

This document designs future parser and redaction hardening for real
`active_nmap_basic` output, using the already documented technical smokes as
reference material. It is documentation-only. It does not run Docker, run Nmap,
run `nmap --version`, perform DNS checks, send HTTP traffic, probe targets,
start Compose, change backend/frontend/runner runtime, add backend-to-
active-tools calls, add a runner HTTP endpoint, create jobs, create exports,
integrate archive/run-all, integrate Active into `tools/runner/main.py`, approve
new targets, approve `www.vildek.es`, approve `app.vildek.es`, approve port
`80`, create a tag, or create a release.

## Real Fields Observed

The documented own-domain smoke against `www.urlbreve.es:443` included these
field classes:

- target FQDN supplied by the operator: `www.urlbreve.es`;
- resolved IP reported by Nmap: `51.38.225.243`;
- PTR hostname emitted by Nmap default DNS behavior:
  `vps-40567620.vps.ovh.net`;
- port observation: `443/tcp`;
- state and reason: `open`, `syn-ack`;
- service table label: `https`, method `table`;
- raw Nmap args embedded in XML;
- exact start and finish timestamps;
- local XML stylesheet reference using a `file://` path inside the image;
- runstats such as elapsed time, host counts, and exit status.

The container-loopback smoke also included the expected bounded local
observation `127.0.0.1:65000/tcp closed conn-refused`, with no hostnames because
that run used `-n` and Docker `--network none`.

## Sensitivity Classification

Normal structured result fields:

- `audit_type`;
- fixed profile name;
- target kind such as `authorized_fqdn` or `container_loopback`;
- display-safe target label after target-policy and redaction review;
- TCP port number that was explicitly requested and accepted;
- protocol when it is exactly `tcp`;
- state when it is in a small allowlist;
- reason when it is in a conservative allowlist;
- coarse `observed_at` if needed;
- `manual_validation_required: true`;
- `result_interpretation: observed_exposure_review_indicator`.

Fields to omit by default:

- exact Nmap start and finish timestamps unless a future retention/audit design
  needs coarse timing;
- Nmap runstats details beyond controlled execution status and bounded elapsed
  category;
- service table labels unless a future parser explicitly keeps only low-risk
  labels.

Fields to redact or drop before storage/API/report/export/Raw JSON:

- raw XML;
- raw command args;
- raw stdout;
- raw stderr;
- PTR hostnames;
- hostnames not supplied by the user;
- resolved IP for FQDN targets;
- local file paths;
- stylesheet references;
- service banners, versions, fingerprints, and method details;
- any reverse-DNS or DNS-derived value not explicitly introduced by the user.

Fields allowed only in manual documentation records:

- the exact raw XML snippet from the executed smoke;
- the resolved IP `51.38.225.243`;
- the PTR hostname `vps-40567620.vps.ovh.net`;
- exact command evidence and timestamps from the one-shot smoke.

Fields that must never reach public report/export/Raw JSON surfaces in v0:

- full raw XML;
- raw command args;
- raw stdout/stderr;
- PTR hostname;
- hostnames not supplied by the user;
- stylesheet `file://` references;
- local paths;
- service/banner/version data;
- DNS reverse-lookup data;
- unreviewed resolved IP values for FQDN targets.

## Structured Payload V0

A future hardened `active_nmap_basic` structured payload should allow only:

```json
{
  "audit_type": "active_nmap_basic",
  "profile": "tcp_connect_small",
  "target_kind": "authorized_fqdn",
  "target_display": "authorized target",
  "observations": [
    {
      "port": 443,
      "protocol": "tcp",
      "state": "open",
      "reason": "syn-ack",
      "observed_at": "coarse-or-omitted",
      "manual_validation_required": true,
      "result_interpretation": "observed_exposure_review_indicator"
    }
  ]
}
```

The target display value should be generated by policy, not copied from raw XML.
For container-loopback smoke, `target_kind` may be `container_loopback`. For an
authorized FQDN, `target_kind` may be `authorized_fqdn`. This field must not be
used to imply independent ownership proof.

Blocked or redacted from the structured payload:

- raw XML;
- raw command args;
- raw stdout;
- raw stderr;
- PTR hostname;
- resolved IP in report or visible Raw JSON for FQDN targets unless a later
  explicit decision changes this;
- exact timestamps if they are not needed;
- service/banner/version fields;
- local file paths;
- stylesheet references;
- non-user hostnames;
- reverse-DNS data.

## PTR Policy

PTR output must be treated as unsolicited and potentially sensitive data.

V0 policy:

- do not show PTR hostnames in UI, API, report, export, or Raw JSON;
- do not persist PTR hostnames in backend debug payloads by default;
- do not treat PTR as target identity, ownership proof, or vulnerability
  evidence;
- do not include PTR in summaries, findings, observations, or user-facing copy;
- document PTR only in manual smoke records when needed to explain a hardening
  gap.

If future execution should prevent PTR at the source, design a separate
IP-freeze plus `-n` phase. That phase must freeze the exact IP, authorization
context, risk tradeoff, and result interpretation before any execution.

## IP Policy

For FQDN targets, the resolved IP is useful operational context but can reveal
hosting, routing, and infrastructure details that were not explicitly submitted
as the target.

Recommended v0 policy:

- omit observed resolved IP from public reports and visible Raw JSON for exact
  FQDN targets;
- store only a neutral internal marker such as `resolved_target_observed: true`
  if a future implementation needs to know resolution happened;
- avoid storing raw resolved IP unless a separate internal retention/redaction
  decision requires it;
- show an IP only when the target was an explicitly frozen IP literal and the
  report display policy has accepted that exact behavior.

Options intentionally not accepted here:

- showing resolved IP by default for FQDN targets;
- using resolved IP as a finding;
- using resolved IP to expand scans;
- keeping a reverse-DNS name beside the IP;
- treating a resolved IP as permission to scan adjacent hosts or ports.

## Parser Hardening

A future parser hardening implementation should:

- truncate stdout/stderr before parsing and record `output_truncated`;
- parse only machine-readable XML within bounded byte limits;
- extract only allowlisted fields;
- discard all hostnames with `type="PTR"`;
- discard hostnames not explicitly supplied by the user;
- ignore `address` values for FQDN targets by default;
- keep IP literals only when the original accepted target was an IP literal;
- ignore service data by default, or keep only a separately reviewed table label;
- never trust `reason` for vulnerability, exploitability, safety, or coverage
  claims;
- allow only conservative reasons such as `syn-ack`, `conn-refused`, `reset`,
  `timeout`, or controlled unknown states if reviewed;
- treat malformed XML as a controlled parser state;
- treat truncated XML as controlled `truncated` or `malformed_truncated`;
- treat multiple hosts as unsupported shape for v0;
- treat hostnames or addresses that do not match the accepted target policy as
  unsupported shape;
- treat multiple ports as unsupported if they were not in the frozen accepted
  request;
- reject or mark unsupported any unexpected scan type, protocol, script output,
  service/version block, OS data, or NSE section;
- return controlled statuses rather than raw parser exceptions.

The parser should minimize first, then redaction should run again at backend
storage/API/report/export/UI/Raw JSON boundaries. Redaction is a defense layer,
not permission to keep raw output.

## Report Wording

Allowed wording:

- "observed TCP exposure";
- "review indicator";
- "manual validation required";
- "observed for the exact authorized target at the time of execution";
- "bounded `tcp_connect_small` observation".

Blocked wording:

- vulnerability claim;
- exploitability claim;
- target-safety claim;
- secure or insecure production claim;
- all-ports-found claim;
- full-scan claim;
- ownership proof claim;
- public-scanner claim.

An `open` TCP state should be rendered only as an observed TCP exposure /
review indicator. A `closed` TCP state should be rendered only as an observation
for the exact target and port, not as proof that a system is safe.

## Future Tests

Recommended future tests:

- fixture XML with a PTR hostname;
- fixture XML with the `https` service table label;
- fixture XML with raw args embedded in the root node;
- fixture XML with multiple hostnames;
- fixture XML with malformed content;
- fixture XML with truncation;
- fixture XML with multiple hosts marked unsupported;
- fixture XML with unexpected hostnames or addresses marked unsupported;
- fixture XML with multiple ports checked against accepted request ports;
- ensure PTR, resolved IP for FQDN targets, raw args, raw XML, stylesheet
  references, and raw stdout/stderr do not appear in API responses, reports,
  exports, or Raw JSON;
- ensure port, protocol, state, and allowlisted reason appear only in
  conservative structured observations.

Tests should use synthetic fixtures unless a separately approved phase freezes a
new real-output fixture. No test should require Docker, Nmap, DNS checks,
external HTTP traffic, or live targets by default.
